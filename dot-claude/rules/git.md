# Git ルール(全プロジェクト共通)

すべてのリポジトリでの Git 操作はこのルールに従う。
プロジェクト側の CLAUDE.md に別のルールがある場合はそちらを優先する。

## ブランチ運用

- `main` / `master` には直接コミットしない。必ず作業ブランチを切る。
- ブランチ名は `<type>/<短い説明>` 形式(kebab-case)。
  - 例: `feat/user-auth`, `fix/login-redirect`, `docs/readme-update`, `chore/deps-bump`
  - Issue に紐づく場合は `feat/123-user-auth` のように番号を含める。
- 作業開始前に `git fetch` して最新の main から分岐する。

## コミット

- メッセージは英語で、Conventional Commits 形式を使う:
  - `feat:` 新機能 / `fix:` バグ修正 / `docs:` ドキュメント / `refactor:` リファクタリング
  - `test:` テスト / `chore:` 雑務(依存更新・設定変更など) / `ci:` CI 設定
- 1 行目(サマリー)は 72 文字以内・命令形。必要なら空行を挟んで本文に「なぜ」を書く。
- 1 コミット = 1 つの意味のある変更。無関係な変更を混ぜない。混在している場合は分割を提案する。
- コミット前に差分を確認し、デバッグコード・秘密情報(API キー、トークン、.env)が
  含まれていないことを確認する。

## プッシュ・履歴操作

- `git push --force` は禁止。自分だけの作業ブランチに限り `--force-with-lease` を使ってよい。
- 共有ブランチ(main、他人も触るブランチ)の履歴書き換え(rebase / amend 後の push)はしない。
- `git reset --hard` や `git clean` などの破壊的操作は、実行前に必ず確認を取る。

## プルリクエスト

- PR タイトルもコミットと同じ Conventional Commits 形式。
- PR は小さく保つ(目安: 差分 400 行以内)。大きくなる場合は分割を提案する。
- マージ方式は squash merge を基本とする(プロジェクト側の慣習があればそちらに従う)。
- マージ済みブランチは削除する。

## やってはいけないこと

- 生成物(ビルド成果物、`node_modules` 等)や秘密情報のコミット。`.gitignore` を先に整備する。
- `git add -A` での無確認一括ステージ(必ず差分を見てからステージする)。
- コンフリクト解消時に、理解しないまま片側を機械的に採用すること。
